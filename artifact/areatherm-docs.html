DRDO Innovation Challenge — Area-Specific Shelter Design

AreaTherm Documentation

"Design the shelter for the climate — not the climate for the shelter."

A physics-based decision-support platform that predicts thermal performance and optimizes passive shelter design for a specific location — built for "Software Based Model Development for Design of Area Specific Shelter for Thermal Comfort Maintenance," initial focus: Ladakh, extensible to any climate.

Prototype: HTML/CSS/vanilla JS, zero dependencies Live weather: Open-Meteo + NASA POWER (10 locations) Target stack: Angular 18 + Spring Boot 3 + MySQL 8
▶ Open Live App Source on GitHub

§0 Overview

What AreaTherm is, who it's for, and how this document is organized.

AreaTherm turns "design a shelter" from a rule-of-thumb exercise into a modeled, comparable, optimizable decision. A user picks a location, describes a shelter, and the platform runs a real hourly heat-balance simulation, generates and scores dozens of alternative designs, and recommends the one that holds comfort best for that specific climate — with every number traceable back to the formula that produced it.

Primary users

DRDO researchers, agricultural scientists, rural development departments, civil/building engineers, architects, government agencies and NGOs. A Guided Setup wizard (§ Modules) extends usability to non-technical stakeholders — farmers, cold-region infrastructure developers, rural housing planners — without touching the underlying model.

How to read this document

§1–3 explain what the system does and its shape. §4–7 are the engineering core — the actual physics, optimization math, and data contracts. §8–11 cover where it runs today, what it doesn't do yet, and where it's going.

§1 Problem Statement

Why area-specific passive design matters, using Ladakh as the founding case.

Ladakh receives roughly 1,900–2,100 kWh/m²/year of solar irradiance, ~7.9 hours of sunshine per day, and over 300 cloud-free days annually — enormous passive heating potential. Yet after sunset, indoor temperature in most existing shelters collapses toward ambient because of high envelope heat loss, poor insulation, inappropriate material selection, poor orientation, oversized openings, air leakage, and a near-total absence of thermal mass to carry daytime heat into the night.

None of these failure modes are location-agnostic — a wall system that performs well in Nagpur's tropical plain can perform terribly in Drass's cold desert, and vice versa. The objective is a software model that predicts and recommends the shelter design best suited to a specific location's climate, rather than applying one generic design everywhere.

§2 Design Workflow

The pipeline every simulation run passes through, end to end.

flowchart TD
  A[User Input] --> B[Climate + Location Data]
  B --> C[Shelter Design Parameters]
  C --> D[Material Database]
  D --> E[Thermal Model]
  E --> F[Simulation]
  F --> G[Multi-Parameter Optimization]
  G --> H[Recommended Shelter Design]
  H --> I[Thermal Performance Report]

In the app, this maps to a 15-step user journey: create project → select location → load climate data → define comfort requirement → define geometry → select materials → define openings → add thermal mass → run simulation → view performance → run optimization → compare designs → select recommended design → run what-if analysis → generate report. The Guided Setup wizard collapses this into 5 plain-language steps for non-engineers; every advanced screen remains available for full control.

§3 Architecture

What's actually running today, and the production system it's designed to become.

Why a JS prototype, not Angular/Spring Boot: the development environment has no Java 17+/Maven/Node/npm/Docker toolchain — only a bare Java 8 JRE. Writing Angular/Spring Boot source that cannot be compiled or run there would produce unverifiable scaffolding. Instead, the entire workflow — including the real physics engine and optimizer — runs as a dependency-free client-side app, so every claim in this document is something you can open the live app and check.

What's running now

A static HTML/CSS/vanilla-JS single-page app (no build step, no framework, no backend). State persists to the browser's localStorage, field-compatible with the schema in §7 so a future API swap is a data-layer change, not a redesign. Deployed as a static site via GitHub Pages (§8). The sidebar becomes an off-canvas drawer (hamburger toggle) below 860px width, so the same deploy works on a phone without a separate mobile build.

Shelter Designer

Materials
Editable library across wall/roof/insulation/thermal-mass/window categories; add custom materials, all labelled "engineering database — verify for construction."
Thermal Simulation
Runs the hourly RC model (§6), indoor-vs-ambient-vs-comfort chart, heat-flow breakdown, and per-term "Explain Calculation" panels.
Optimization
Generates ~60 candidate designs, scores them on a configurable weighted formula (§7), ranks top 5, recommends the best, runs sensitivity analysis.
What-If Analysis
Single-parameter before/after comparison (insulation, orientation, window area, thermal mass, roof material).
Validation
Enter measured field data; computes MAE/RMSE/MAPE/R² against the model's prediction and plots measured-vs-predicted.
Reports
Assembles a full engineering report (methodology, assumptions, results, limitations, disclaimer) — print/PDF via the browser.
Evaluator Summary
A 2–3 minute story for a reviewer: location, climate severity, comfort score, recommended design, "why this design."
Settings
Units reference, full assumptions register, project name, session reset.

§5 Live Weather & Reference Locations

How real data gets into the model, and how it's kept honest.

Every one of the 10 reference locations gets its climate from three live sources working together — no hand-authored or illustrative climate dataset ships with the app at all — plus custom lat/lon entry for any point on Earth:

✓ Open-Meteo — drives the simulation. A live 7-day forecast fetched directly from the browser (CORS-enabled, no API key, no backend needed). The hourly series across those 7 days is bucketed by hour-of-day and averaged into a "typical day" curve, which the thermal model consumes directly — smoothing out any single unusually cloudy or windy day. Source: app/js/weather-api.js.

✓ NASA POWER — real annual solar/temperature climatology. A 20-year (2001–2020) climate normal for solar irradiance (GHI, DNI, diffuse) and 2 m air temperature, fetched separately from Open-Meteo. This is what backs the "annual solar potential" figure — a real long-term average, not an extrapolation from the 7-day forecast. Source: app/js/nasa-power.js.

✓ Open-Meteo Elevation API — real elevation. SRTM-derived, no key required, fetched independently of weather/climatology so a failure in one source never blocks the others. Source: app/js/elevation.js.

Every screen showing climate-derived numbers displays a data-source badge naming exactly which of these produced it. A shared reliability layer (app/js/reliability.js) wraps every one of these calls with a request timeout, capped exponential-backoff retries, a per-source circuit breaker, and a tiered live → fresh-cache → stale-cache fallback — the badge always reflects which tier actually served the number, never silently shown as live.

§6 Thermal Model

The physics — transparent by design, reproducible in-app via "Explain Calculation" on every number.

A single-zone, two-node lumped-capacitance (RC) network, solved by implicit (backward-Euler) time-stepping at 15/30/60-minute resolution. Two temperature nodes — indoor air (T_air) and thermal mass (T_mass) — make the charge/discharge behaviour of thermal mass visible rather than hand-waved. Backward-Euler is unconditionally stable, which matters here because indoor-air capacitance is small relative to hourly heat-flow magnitudes — explicit Euler diverges on this system.

6.1 — Sol-air temperature (opaque surfaces)

T_sol-air(t) = T_amb(t) + (α_surface × G_surface(t)) / h_o
// α = solar absorptivity · G = irradiance on that surface · h_o = outside film coeff. (23 W/m²K, wind-adjusted)

Folds opaque-surface solar gain into the conduction term — standard ASHRAE sol-air practice. Longwave sky-radiation correction is omitted (disclosed assumption).

6.2 — Conduction losses/gains

Q_wall = U_wall × A_wall × (T_air − T_sol-air,wall)
Q_roof = U_roof × A_roof × (T_air − T_sol-air,roof)
Q_floor = U_floor × A_floor × (T_air − T_ground)
Q_window,cond = U_window × A_window × (T_air − T_amb)

6.3 — Solar heat gain through glazing

Q_solar,window = Σ_windows A_window × G × orientation_factor × SHGC

6.4 — Ventilation / infiltration

Q_vent = ACH × Volume / 3600 × ρ_air × Cp_air × (T_air − T_amb)
// ρ_air = 1.2 kg/m³ · Cp_air = 1005 J/kg·K

6.5 — Orientation factor

A piecewise table over angle from due south (documented assumption, user-editable): South 1.00 · SE/SW 0.85 · East/West 0.55 · NE/NW 0.30 · North 0.15 — interpolated linearly, or computed from a true azimuth when a custom angle is entered.

6.6 — Thermal mass node

Q_exchange = h_mass × A_mass × (T_air − T_mass)
C_mass × dT_mass/dt = Q_exchange + f_solar_to_mass × Q_solar,window
// C_mass = mass × Cp_material · PCM uses an elevated apparent Cp over its melt band

6.7 — Indoor air energy balance

C_air × ΔT_air/Δt = Q_solar,window + Q_internal − Q_exchange
    − Q_wall − Q_roof − Q_floor − Q_window,cond − Q_vent
// C_air = Volume × ρ_air × Cp_air

6.8 — Derived outputs

  • Comfort hours — count of timesteps with comfort_min ≤ T_air ≤ comfort_max
  • Heating/cooling requirement — auxiliary energy that would hold comfort during out-of-band hours
  • Solar utilization % — share of solar energy striking the glazing aperture that is actually transmitted (bounded well under 100% by construction — not a gain-vs-loss ratio, which would saturate)
  • Heat retention % — gains (solar + internal + net mass release) as a share of total losses
  • Thermal Comfort Score (0–100) — 0.45×comfort + 0.25×retention + 0.20×solar-utilization + 0.10×energy-adequacy

Every formula above is re-printed with the run's actual substituted numbers in the in-app "Explain Calculation" panel for that term — nothing is a black box.

§7 Optimization Methodology

A weighted multi-criteria search over a sampled design space — not a black-box recommendation.

flowchart TD
  A["Baseline design + variable ranges"] --> B["Candidate generator
(orientation × wall system × insulation × window % × glazing × thermal mass)"]
  B --> C["Thermal engine run per candidate (§6)"]
  C --> D["Weighted multi-criteria score"]
  D --> E["Rank -> Top 5 (Design A-E)"]
  E --> F["Sensitivity analysis:
perturb one parameter, measure Δ score"]

Default weights (user-adjustable, live)

CriterionDefault weightWhat it measures
Thermal Comfort40%Comfort-band hours, day + night
Heat Retention25%Gains as a share of total losses
Solar Utilization15%Transmitted vs. incident solar on glazing
Energy Efficiency10%Auxiliary heating/cooling demand, normalized across the candidate batch
Cost10%Materials-based cost estimate, normalized across the candidate batch

~60 candidates are evaluated per run (sampled across orientation × insulation thickness × window % × glazing type × thermal-mass level). An optional ML surrogate layer is architected but not built — no labelled field data exists yet to train or validate one, and the brief explicitly prohibits claiming ML accuracy without validation data.

§8 Database Schema (production target)

MySQL 8 schema the Spring Boot backend would run against — not deployed in this environment (no MySQL/Docker here).

Sixteen entities, matching the brief's data-architecture requirement one-for-one: app_user, project, location, predefined_location, climate_profile (+ climate_profile_hourly time series), comfort_profile, material, shelter_design, opening, thermal_mass, simulation (+ simulation_result time series), optimization_run, design_candidate, validation_dataset (+ validation_dataset_point), report, audit_log.

Every climate_profile row carries data_source, api_source, data_validation_status (REAL | ILLUSTRATIVE), and last_fetched — the exact fields the frontend's data-source badge (§5) reads from, so the transparency guarantee holds all the way down to the database, not just the UI layer.

§11 Limitations & Scientific Integrity

What this platform does not claim, and the assumptions it discloses.

Never fabricated: experimental measurements, DRDO validation, material test results, weather observations passed off as field data, accuracy percentages, energy or cost savings. Every number on screen is labelled as one of: input data, model assumption, calculated result, or (where user-supplied) field measurement — never blurred together.

Not yet implemented

  • Authentication / RBAC persistence, multi-user shared database (state is per-browser localStorage today, with multiple named projects and offline app-shell caching via a service worker)
  • ERA5/IMD archive integration — NASA POWER covers solar/temperature climatology and Open-Meteo's Elevation API covers real elevation; other historical variables (precipitation, detailed wind climatology) would need these
  • The 3D shelter preview is an illustrative box approximation — it doesn't yet model curved or L-shaped footprints, and door/window placement isn't tied to the per-face data model used elsewhere
  • Server-side PDF rendering (browser print-to-PDF instead)
  • ML surrogate model (architected in the source ARCHITECTURE.md, not trained — no labelled field data exists)
  • The Imperial/metric toggle is display-only — the engine and every calculation stay metric internally

Disclosed modeling assumptions

Transient (hourly RC), not steady-state. Outside film coefficient fixed at 23 W/m²K, wind-adjusted infiltration. Sky longwave radiation folded into the sol-air simplification. Ground temperature defaults to seasonal mean ambient unless overridden. Internal gains constant-per-hour unless an occupancy schedule is supplied. PCM modelled via elevated apparent specific heat over its melt band, not full enthalpy method.

§12 Roadmap

The path from this prototype to the full production system.

  1. Stand up the Spring Boot/MySQL backend against DATABASE_SCHEMA.sql and API_SPEC.md; port engine.js to a Java thermal service — largely a language port, not a redesign, since it's already framework-free.
  2. Wire an Angular frontend to that API in place of store.js.
  3. Instrument a pilot shelter in Leh or Kargil and feed real readings into the Validation module to get an actual MAE/RMSE against the model.
  4. Add ERA5 / IMD archive adapters behind the existing ClimateProfile abstraction, for historical variables beyond what NASA POWER's climatology already covers.
  5. Train an ML surrogate once enough simulation + field-validation data exists, kept clearly labelled "ML-based estimation" and never merged with physics-model results.
